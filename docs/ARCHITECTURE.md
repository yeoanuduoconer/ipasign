# Architecture and Protocol Notes

This document records what each layer of ipasign does and the Apple protocol details involved, to make secondary development easier.

## Layers

```
┌───────────────────────────────┐
│  app.py  →  tui.py / cli.py   │  Interaction layer: I/O and orchestration only
├───────────────────────────────┤
│  apple/   auth · developer ·  │  Service layer: all networked Apple interactions
│           issue · anisette    │
├───────────────────────────────┤
│  core/    macho · cms · bundle│  Engine layer: pure computation, offline, reusable on its own
│           ipa · pki · vault   │
├───────────────────────────────┤
│  device.py (pymobiledevice3)  │  Device layer: install / query
└───────────────────────────────┘
```

`core/` does not import `apple/`, so a batch-signing script can run with only `cryptography` installed.

## 1. Mach-O Code Signing

The signature of an iOS executable is "a block of data appended to the end of the file", pointed to by
`LC_CODE_SIGNATURE`:

```
SuperBlob (0xFADE0CC0)
├── 0x0000 CodeDirectory (0xFADE0C02, version 0x20400)
├── 0x0002 Requirements    (0xFADE0C01)
├── 0x0005 Entitlements    (0xFADE7171, XML plist)
├── 0x0007 DER entitlements(0xFADE7172, Apple DER plist)
└── 0x10000 CMS            (BlobWrapper 0xFADE0B01)
```

**CodeDirectory** is the core: it stores

- `codeLimit`: the number of bytes covered by the hash (= the signature start offset)
- one SHA-256 per 4096 bytes (`nCode` of them)
- the special slots (`nSpecial`): Info.plist, Requirements, CodeResources, XML/DER entitlements
- `teamID`, `execSegBase/Limit/Flags`

Generation order (`core/macho.py::sign_macho`):

1. Parse the load commands and locate `LC_CODE_SIGNATURE` and `__LINKEDIT`
2. Truncate the old signature and place the signature area at a 16-byte-aligned offset
3. Build CodeDirectory → SuperBlob → compute the CMS
4. Because `datasize`/`__LINKEDIT.filesize` are written inside the hashed header, this needs to **iterate to convergence** (usually 2 rounds)

### Common Pitfalls

| Pitfall | Symptom | Handling |
| --- | --- | --- |
| Signature area not 16-byte aligned | iOS `0xe8008019` invalid signature | `_pad_signature()` zero-pads |
| DER entitlements (slot 7) missing | iOS 26 `0xE8008029` unsupported signature version | generated by `core/derplist.py` |
| Resource seal misses nested files | verification fails during install | `resources.py` excludes only the root `_CodeSignature` |
| `execSegFlags` reset | some Apps behave incorrectly | preserve the flags of the original signature |

### DER entitlements Format

Apple uses a compact DER encoding, confirmed byte by byte against `zsign` output:

```
70 <len>            root (APPLICATION 16)
  02 01 01          INTEGER 1, version
  b0 <len>          dictionary (CONTEXT 16)
    30 <len>        each key/value pair is a SEQUENCE
      0c <len> key  UTF8String
      <value>       0c string / 01 boolean / 02 integer / 30 array / b0 nested dictionary
```

Keys are sorted in ascending byte order. The output of `core/derplist.py::encode_entitlements` is
byte-for-byte identical to zsign (a test pins this vector).

## 2. CMS / PKCS#7

`core/cms.py` hand-writes DER to generate the CMS:

- `SignedData` + `SignerInfo` (version 1)
- digest algorithm SHA-256, signature algorithm `rsaEncryption`
- signed attributes: `contentType`, `messageDigest`, `signingTime`, plus Apple's two
  hash-agility attributes:
  - `1.2.840.113635.100.9.1` (cdhash, octet string)
  - `1.2.840.113635.100.9.2` (plist wrapper of the cdhash)
- the certificate chain is embedded in leaf → WWDR G3 → Apple Root CA order

Verification uses `verify_detached_cms` (our own implementation) or `openssl cms -verify`.

## 3. Certificate Factory (Developer API)

Protocol `QH65B2`, endpoint:

```
POST https://developerservices2.apple.com/services/QH65B2/<action>.action?clientId=XABBG36SBA
Content-Type: text/x-xml-plist
```

The request body is a plist, with these common fields:

```
clientId        XABBG36SBA
protocolVersion QH65B2
requestId       uppercase UUID
userLocale      en_US
teamId          team ID
```

Actions used:

| action | Purpose | Key fields |
| --- | --- | --- |
| `listTeams` | list teams | — |
| `ios/listDevices` | list devices | — |
| `ios/addDevice` | register a device | `deviceNumber` (UDID), `deviceName` |
| `ios/listAllDevelopmentCerts` | list certificates | — |
| `ios/submitDevelopmentCSR` | request a certificate | `csrContent` = **base64(DER)** |
| `ios/revokeDevelopmentCert` | revoke | `certificateId`, `serialNumber` |
| `ios/addAppId` | register an App ID | `identifier`, `name` |
| `ios/downloadTeamProvisioningProfile` | fetch a provisioning profile | `appIdId` |

The response may be **a plist or JSON** (on errors); the parser supports both.
A non-zero `resultCode` means failure: `3250` malformed CSR, `7460` certificate count at the limit,
`35` missing required parameter.

> A free account has `maxActive: 1` per type, so when switching Apps, reuse the certificate and only re-download the profile
> (`ipasign issue --reuse`).

### Protecting the Private Key When Requesting a Certificate

After the CSR is generated, the private key is first written to `~/.ipasign/pending-key.pem`, and it is deleted only after signing succeeds.
The reason: once Apple signs a CSR it consumes one certificate slot, so if the process crashes at that point, losing the private key
would leave that certificate permanently unusable (the only remedy is to revoke it and start over).

## 4. GrandSlam Login

Login goes through Apple's SRP-6a:

1. `init`: send `A2k` (client public key), `ps` (supported preprocessing), `cpd` (device data)
2. the server returns `s` (salt), `B` (server public key), `i` (iteration count), `c` (challenge)
3. `complete`: send `M1` (client proof), `c`
4. the server returns session tokens (`GsIdmsToken`, `sk`, `t`, etc.)

ipasign does not rewrite this flow in Python; it calls a locally compiled `apple_auth_client`
(MIT), because that flow also contains a lot of edge-case handling such as 2FA, trusted devices, and app token exchange.

**App tokens** (`o=apptokens`, `app=com.apple.gs.xcode.auth`) are the prerequisite for calling the developer API;
the exchange uses `sk` to compute HMAC-SHA256 over `"apptokens" + dsid + app` as the
`checksum`. The challenge value in this step is one-shot: after a 503 you must log in again.

## 5. Device Attestation (ADI v3)

Apple requires every request to carry `X-Apple-I-MD` (a one-time password), which is derived from the ADI file and
the device fingerprint. ADI file layout:

```
4B  version (3)
4B  prefix length
NB  prefix
16B IV
NB  AES ciphertext (multiple of 16)
20B authentication tag
```

The ciphertext key comes from "hardware fingerprint + prefix" run through a custom MD5 diffusion
(319-byte state, 128-byte table, 1276 mixing steps), so **the ADI is bound to the machine that generated it**. This part is implemented with a native
library (`apple_auth.dll`); Python only makes ctypes calls.

The flow for provisioning an ADI yourself (`apple/anisette/provision.py`):

```
GET  /grandslam/GsService2/lookup                → midStartProvisioning / midFinishProvisioning
POST midStartProvisioning  {Header:{}, Request:{}}            → Response.spim
     cpim = aauth_provisioning_begin(spim, hardware fingerprint) → aauth_provisioning_request()
POST midFinishProvisioning {Request:{cpim: b64}}             → Response.ptm / tk / RINFO
     aauth_provisioning_finish(ptm, tk) → export adi.pb
```

The request headers must include:

```
X-Mme-Device-Id   stable device UUID (the server binds the entity to it)
X-Apple-I-MD-LU   stable hex string (uppercase, not UUID format)
X-MMe-Client-Info the Windows-platform one is <PC> <Windows;6.2(0,0);9200> <com.apple.AuthKitWin/1 ...>
Content-Type      application/x-www-form-urlencoded (even if the body is a plist)
```

A platform mismatch yields `-29003 environment mismatch`; a missing device ID yields
`-29000 EntityNotAvailable`.

## 6. Installation

`device.py` calls `pymobiledevice3 apps install`, and after installing it uses
`pymobiledevice3 apps list` to confirm that the bundle id really appears (iOS sometimes "reports success"
but actually discards it), retrying 5 times to work around list refresh latency.

## 7. Automatic Renewal

ipasign/watch.py is a very thin scheduling layer:

`
renewals.json            # jobs: ipa / vault entry / device / interval
   ↓ run_once(threshold)
profile expiry ≤ threshold?
   ↓ yes
issue(reuse=entry)       # re-fetch the profile (reuse the same certificate)
   ↓
sign_ipa(old IPA → new IPA)
   ↓
install_ipa(udid, wifi)
   ↓
record last_run / last_result / last_error
`

Key points:

- **Refresh the provisioning profile only, do not re-issue the certificate** — a certificate is valid for a year, a profile expires in 7 days, and re-issuing a certificate consumes the single slot on a free account.
- The expiry time is read from meta.profile_expires in the certificate vault; when the metadata is missing it falls back to parsing the provisioning profile itself.
- Passwords are not written to disk by default; only --save-password writes them into the job file (plaintext, trusted local environment only).
- watch start is a foreground loop; when it needs to run unattended, use a system scheduler (Windows Task Scheduler / systemd timer / cron) to invoke watch run.

## 8. Wi-Fi Installation

Installation uses the classic lockdown + installation_proxy path and does not need the RSD tunnel of iOS 17+;
usbmuxd routes the connection to a USB or network device by UDID.

Therefore the prerequisite for Wi-Fi is that the device **has already been paired for Wi-Fi sync**:

1. Connect once with a cable and tick "Sync over Wi-Fi" in iTunes (Windows) / Finder (macOS)
2. The phone and the computer are on the same LAN, and the phone is unlocked
3. pymobiledevice3 usbmux list --network can see the device

list_devices(wifi=...) filters on DeviceInfo.transport (usb / wifi);
when install_ipa(..., wifi=True) cannot find a network device it prints the guidance above.

## 9. Pitfall Log: 0xe8008019 and cdhash Truncation

Symptom: our own signature was rejected on iOS 26 (`0xe8008019`), while a zsign signature of the same
content could be installed, and our CMS verified successfully with OpenSSL.

Debugging method: keep zsign's CodeDirectory and replace only the CMS with ours — it still failed,
so the scope narrowed to the CMS. Comparing attributes one by one revealed that in Apple's hash-agility attribute
(`1.2.840.113635.100.9.1`, whose content is an XML plist of `{cdhashes: [<data>]}`):

- zsign: the **first 20 bytes** of `SHA-256(CodeDirectory)`
- ours: the full 32 bytes

Apple's cdhash is itself a SHA-256 truncated to 20 bytes; iOS compares it with the actual CD,
and the extra 12 bytes make the whole signature invalid.

Fix: write `cdhash[:20]` when generating that plist; `1.2.840.113635.100.9.2` (the DER form)
still keeps the full 32-byte SHA-256, consistent with codesign/zsign. See `tests/test_cms.py` for the regression test.
